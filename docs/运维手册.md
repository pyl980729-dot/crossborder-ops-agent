# 运维手册

面向负责日常运维的人：怎么确认系统正常、出问题怎么查、日志在哪、什么不能做。

---

## 一、进程与端口

| 项 | 值 |
|---|---|
| 启动命令 | `python run.py`（默认 `127.0.0.1:8000`） |
| 自定义端口 | `python run.py --port 8080` |
| 健康检查 | `GET /api/health` |
| 工作进程数 | **必须 1**（内置调度器按单进程设计） |
| 常驻方式 | systemd（见部署手册）或 `docker compose` |

### 确认是否在运行

```bash
curl -s http://127.0.0.1:8000/api/health
# {"status":"ok","llm":{"mode":"offline",...},"stages":7}
```

返回 `mode=offline` 说明当前是离线规则模式，不影响功能完整性。

## 二、日志

### 位置与格式

| 项 | 值 |
|---|---|
| 文件 | `data/logs/app.log` |
| 控制台 | 同时输出到 stdout |
| 滚动 | 单文件 5 MB，保留 3 份备份（共 4 个文件） |
| 格式 | `时间 \| 级别 \| 模块 \| 消息` |
| 级别 | 由 `ECOM_LOG_LEVEL` 控制，默认 `INFO` |

### 记录了哪些模块

| logger | 覆盖内容 |
|---|---|
| `app` | 每个 HTTP 请求：request_id、方法、路径、状态码、耗时；401 单独记；服务启动/停止 |
| `orchestrator` | 运行开始、每个回流、运行结束汇总、闭环判定 |
| `stage` | **每个环节的运行结果**：状态、耗时、解读数、动作数、P0 数、回流数、头条 |
| `review_classify` | 归因分布：总量、需归因数、规则/模型/人工/待确认、覆盖率 |
| `datasets` | CSV 解析结果：类型、行数、跳过行、忽略列、日期范围、警告数 |
| `scheduler` | 定时任务执行成功/失败、cron 非法、tick 异常 |
| `api` | 登录成功/失败、配置修改、数据集上传/删除、成员变更 |

### 一次运行的完整日志长这样

```log
INFO  orchestrator | run start run_id=dbb61fbec0bf stages=7 trigger=manual store=default schedule=-
INFO  stage        | stage=market status=ok elapsed_ms=2 insights=4 actions=4 p0=2 feedback=0 | 月销 56,750 件 …CR3 89.6%
INFO  stage        | stage=strategy status=ok elapsed_ms=1 insights=4 actions=2 p0=1 feedback=0 | 净利率 23.3%，盈亏线 ROAS 4.3
INFO  stage        | stage=listing status=ok elapsed_ms=1 insights=4 actions=3 p0=1 feedback=0 | 最佳 65 字符 / 覆盖 60.0%
INFO  stage        | stage=image status=ok elapsed_ms=0 insights=3 actions=3 p0=1 feedback=0 | 完整性 100.0%
INFO  stage        | stage=video status=ok elapsed_ms=1 insights=4 actions=3 p0=1 feedback=0 | 口播约需 14.9s，时长匹配
INFO  stage        | stage=ads status=ok elapsed_ms=2 insights=10 actions=6 p0=1 feedback=2 | ROAS 6.6 vs 盈亏线 4.3 → P0 1 组
INFO  review_classify | classify total=450 needing=65 auto=0 rule=0/0/0 llm=0 manual=65 pending=0 not_needed=385 coverage=0.000
INFO  stage        | stage=review status=ok elapsed_ms=4 insights=7 actions=7 p0=1 feedback=4 | 好评率 85.6%
INFO  orchestrator | backflow from=ads to=listing count=2 scope=补「注意事项」段…
INFO  orchestrator | run done run_id=dbb61fbec0bf status=ok elapsed_ms=15 ok=7/7 partial=0 blocked=0 actions=28 p0=8 insights=36 backflow=3 baseline=b556f4d3428b
INFO  orchestrator | run cycle run_id=dbb61fbec0bf verdict=持平 better=0 worse=0 stale_p0=8
INFO  app          | [765e0646] POST /api/runs → 200 (43ms)
```

字段都是 `key=value` 形式，可以直接 grep：

```bash
grep "status=blocked" data/logs/app.log        # 哪些环节缺数据
grep "status=error" data/logs/app.log          # 哪些环节计算失败
grep "stage=ads" data/logs/app.log             # 只看广告诊断
grep "run_id=dbb61fbec0bf" data/logs/app.log   # 追一次运行的全过程
grep -E "ERROR|WARNING" data/logs/app.log      # 所有问题
```

### 关键字段含义

| 字段 | 含义 |
|---|---|
| `run_id` | 运行 ID，与「历史」页和 `runs` 表对应 |
| `status=blocked` | 缺必填字段或计算异常，**没有产生结论** |
| `status=partial` | 跑完了但结果不完整（如九宫格缺格） |
| `missing=` | 具体缺哪些字段 |
| `p0=` | 该环节产生的 P0 动作数 |
| `feedback=` | 该环节发出的回流指令数 |
| `baseline=` | 本次对比的历史基线 run_id，`-` 表示首次运行 |
| `stale_p0=` | 上次的 P0 到这次仍未消除的数量 |

## 三、监控建议

| 监控项 | 方式 | 阈值建议 |
|---|---|---|
| 服务存活 | `GET /api/health` 返回 200 | 连续 3 次失败告警 |
| 磁盘空间 | `df` 或监控系统 | 剩余 < 20% 告警 |
| 日志异常 | 统计 `ERROR` 行数 | 10 分钟内 > 5 条告警 |
| 环节阻塞 | 统计 `status=blocked` | 出现即关注（通常是数据问题） |
| 定时任务 | 看「自动化」页 `last_run_at` / `last_error` | 超过一个周期未执行告警 |

外部监控探针可以用服务令牌调用：

```bash
curl -H "X-API-Token: $ECOM_API_TOKEN" http://127.0.0.1:8000/api/health
```

## 四、故障排查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 打开页面一直弹登录 | `ECOM_REQUIRE_LOGIN=1` 且还没建账号 | 访问 `/api/auth/status` 看 `initialized`；为 false 时在页面完成初始化 |
| 所有 `/api` 返回 401 | 未登录，或服务令牌不匹配 | 浏览器登录；脚本调用检查 `X-API-Token` 头 |
| 返回 403 且提示权限不足 | 角色不够 | 用负责人账号操作，或调整成员角色 |
| 上传报 413 | 反向代理限制太小 | Nginx `client_max_body_size` 调到 12m |
| 上传报"缺少必填列" | 列名没匹配上 | 看返回的 `mapping` 与 `current headers`，按使用手册的别名表改列名 |
| 上传报"第 N 行某列不是数字" | 该行有合并单元格或备注 | 清理源文件该行 |
| 定时任务不执行 | `ECOM_SCHEDULER=off`、任务被暂停、或服务已停 | 看「自动化」页状态与 `next_run_at`；查 `scheduler` 日志 |
| 定时任务重复执行 | 起了多个进程/副本 | 只保留一个实例 |
| 启动报端口占用 | 旧进程未退出 | 找到占用 8000 的进程并结束，或换端口 |
| 数据库 `database is locked` | 多进程同时写 | 确认只有一个服务实例；备份脚本用只读连接，不影响 |
| 日志文件不增长 | `data/logs` 无写权限 | 修正权限后重启 |
| 改了阈值没变化 | 没重启，或请求参数/平台预设优先级更高 | 重启；看阈值页每个值的"来源"标注 |
| 页面空白 | 静态文件缺失或反代路径错误 | 确认 `app/static/` 存在；检查 Nginx `proxy_pass` |
| 启动报 `ModuleNotFoundError` | 依赖没装到当前解释器 | 用 `.venv/bin/python` 或 `start.bat` 启动 |

### 排查顺序建议

1. `python scripts/preflight.py` —— 先排除环境问题
2. `grep ERROR data/logs/app.log | tail -20` —— 看最近的异常
3. 拿 `run_id` 去「历史」页看那次运行的完整结果
4. 单点重跑出错环节：`POST /api/stages/{stage}`，缩小范围

## 六、安全

### 必须做的三件事

1. `ECOM_REQUIRE_LOGIN=1` —— 否则任何能访问端口的人都是负责人
2. `ECOM_CORS_ORIGINS` 收紧到具体域名 —— 留空等于允许所有来源
3. 反向代理 + HTTPS，**不要直接把 8000 暴露到公网**

### 建议做

- `.env` 文件权限设为 600（`chmod 600 .env`），不要进版本库
- 负责人密码 12 位以上，定期更换；忘记密码用 `python scripts/reset_password.py <用户名> <新密码>`
- 离职人员及时在「成员」页移除账号
- 服务令牌单独发放给脚本/监控，不要与登录密码混用
- 定期看日志里的登录失败记录：`grep "登录失败" data/logs/app.log`

### 数据边界

- 所有业务数据在客户自己的服务器
- 接大模型时只发送创意类文本（标题、口播稿），分析类数据不出机器
- 上传文件限制 10 MB / 5 万行

## 七、已知限制

| 限制 | 影响 | 缓解 |
|---|---|---|
| 调度器单进程 | 多副本重复触发 | 只跑一个实例，或 `ECOM_SCHEDULER=off` |
| 会话存在服务端单表 | 无 Redis，多实例不共享会话 | 单实例部署 |
| SQLite | 并发写能力有限 | 本系统写入量小，单实例足够；如需集群需改持久层 |
| 平台规则是快照 | 费率/标题上限/图片规格可能过时 | 发布前人工复核；集中在 `app/core/platforms.py` |
| 平台预设为经验值 | CTR 基准等可能与账号实际水平有偏差 | 上线后用自己数据校准 |
| 时间轴按天粒度 | 周/月汇总数据会被当成"最近 N 行" | 导入前确认导出粒度 |
| 日序推断依赖证据 | 整列 01~12 写法时只能按平台习惯猜 | 界面会显示假设，请核对源文件 |
| 评论归因在 65 条样本上评估 | 真实评论更口语化，准确率会低于演示 | 低置信度标"待人工确认" |
| 不执行任何操作 | 不改价、不停广告 | 动作清单交人审批，这是刻意的 |
